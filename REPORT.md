## 2. Описание работы скриптов

### 2.1. `generate_matrices.py`

- Использует `numpy.random.randint` для генерации целочисленных значений.
- Порядок матрицы `n_matrix` задан внутри скрипта (например, `n_matrix = 1000`).
- Записывает `n_matrix` в первую строку текстового файла, затем сгенерированный элементы матрицы построчно.

### 2.2. `verification_matrix.py`

- Загружает матрицы A, B и результат C++ из файлов по фиксированным путям.
- Считывает порядок квадратных матриц `n_matrix` из первой строки каждого файла.
- Вычисляет эталонное произведение через `np.dot` и выполняет точное поэлементное сравнение с результатом C++ с помощью `np.array_equal`.
- При успешном совпадении сохраняет эталонную матрицу в файл `verification_result_C.txt` для возможности визуального анализа и выводит подтверждение в консоль.
- В случае ошибки выводит уведомление и завершает работу.

### 2.3. `matrix_multiplication.cu`

- Матрицы считываются из текстовых файлов и сохраняются в `vector<long long>` как одномерные массивы.
- Доступ к элементу `(i, j)` осуществляется по формуле `i * N + j,` где `N` — порядок квадратной матрицы.
- Вычисления перенесены на `GPU` с помощью ядра `matrixMultiply`.
- Сетка блоков `dim3 blocks` и размер блока нитей `dim3 threads` формируются динамически исходя из порядка матрицы `N` и заданного `block_size`.
- Данные копируются с хоста на устройство через `cudaMemcpyHostToDevice` перед вычислением и обратно через `cudaMemcpyDeviceToHost` после завершения.
- Каждый поток видеокарты отвечает за расчет одного элемента результирующей матрицы `C`, выполняя скалярное произведение соответствующей строки матрицы `A` и столбца матрицы `B` в цикле по `k`.
- Для корректного замера времени используется `cudaDeviceSynchronize()`, которая заставляет центральный процессор дождаться завершения всех операций на `GPU`. Измерение интервала производится с помощью библиотеки `chrono`.
- Результаты замеров (время в мс) и итоговая рассчитанная матрица записываются в `result_C.txt`.

### 2.4. Код `matrix_multiplication.cu`

```C++
%% writefile matrix_multiplication.cu
#include <iostream>
#include <vector>
#include <string>
#include <fstream>
#include <chrono>
#include <cuda_runtime.h>

using namespace std;

vector<long long> read_matrix(const string& filename, size_t& size)
{
    ifstream file(filename);

    if (!file.is_open())
    {
        cerr << "Ошибка: Не удалось открыть файл " << filename << endl;
        exit(1);
    }

    file >> size;
    vector<long long> matrix_value(size * size);
    for (int i = 0; i < size * size; ++i)
    {
        if (!(file >> matrix_value[i]))
        {
            cerr << "Ошибка данных в " << filename << endl;
            exit(1);
        }
    }

    return matrix_value;
}

void write_matrix(const string& filename, const vector<long long>& matrix_flat, size_t& size, double duration_ms)
{
    ofstream file(filename);

    file << size << endl;
    for (size_t i = 0; i < size; ++i)
    {
        for (size_t j = 0; j < size; ++j)
        {
            file << matrix_flat[i * size + j] << (j == size - 1 ? "" : " ");
        }

        file << endl;
    }

    file << "Время выполнения: " << duration_ms << " ms" << endl;
}

__global__ void matrixMultiply(const long long* A, const long long* B, long long* C, size_t N)
{
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;

    if (row < N && col < N)
    {
        long long sum = 0LL;
        for (size_t k = 0; k < N; ++k)
        {
            sum += A[row * N + k] * B[k * N + col];
        }

        C[row * N + col] = sum;
    }
}

int main()
{
    int block_size = 32;

    string file_A = "/content/matrix_A_800.txt";
    string file_B = "/content/matrix_B_800.txt";
    string result_file = "/content/result_C_" + to_string(block_size) + ".txt";

    size_t A_size, B_size;
    vector<long long> h_A = read_matrix(file_A, A_size);
    vector<long long> h_B = read_matrix(file_B, B_size);

    size_t N = A_size;
    size_t bytes = N * N * sizeof(long long);
    vector<long long> h_C(N * N);

    long long* d_A, * d_B, * d_C;
    cudaMalloc(&d_A, bytes);
    cudaMalloc(&d_B, bytes);
    cudaMalloc(&d_C, bytes);

    cudaMemcpy(d_A, h_A.data(), bytes, cudaMemcpyHostToDevice);
    cudaMemcpy(d_B, h_B.data(), bytes, cudaMemcpyHostToDevice);

    dim3 threads(block_size, block_size);
    dim3 blocks((N + block_size - 1) / block_size, (N + block_size - 1) / block_size);

    auto start = chrono::high_resolution_clock::now();
    matrixMultiply << <blocks, threads >> > (d_A, d_B, d_C, N);
    cudaDeviceSynchronize();
    auto end = chrono::high_resolution_clock::now();

    chrono::duration<double, milli> duration = end - start;
    cudaMemcpy(h_C.data(), d_C, bytes, cudaMemcpyDeviceToHost);

    cout << "N = " << N << ", Блок = " << block_size << "x" << block_size << endl;
    cout << "Время выполнения : " << duration.count() << " мс" << endl;

    write_matrix(result_file, h_C, N, duration.count());

    cudaFree(d_A); cudaFree(d_B); cudaFree(d_C);
    return 0;
}
```

## 3. Результаты экспериментов

Работа проводилась в облачной среде `Google Colab`, так как она предоставляет доступ к графическому ускорителю `NVIDIA Tesla T4`.
Это позволило реализовать перенос вычислений на сторону `GPU` с помощью специализированного ядра `matrixMultiply`.
Для демонстрации работы программы были проведены эксперименты с разными конфигурациями сетки блоков (`8x8`, `16x16`, `32x32`)
для матриц порядка `200`, `400`, `800`, `1200`, `1600`, `2000`.

### 3.1. При порядке равном 200

![Зависимость времени от потоков для N=200](Figures/Figure_N=200.png)

- Наименьшее время выполнения (около `0,25 мс`) зафиксировано при использовании блоков `8x8`. Это объясняется тем, что для такой небольшой задачи создание меньшего количества потоков требует меньше ресурсов на планирование со стороны видеокарты.
- Пик времени (более `0,33 мс`) при конфигурации `16x16` не является признаком неэффективности алгоритма, а отражает шум в облачной среде Google Colab.

### 3.2. При порядке равном 400

![Зависимость времени от потоков для N=400](Figures/Figure_N=400.png)

- Общее время выполнения остается крайне низким (менее `0,91 мс`). Как и в предыдущем случае (порядок `200`), время, затрачиваемое на запуск ядер и синхронизацию устройств, сопоставимо с временем чистых вычислений, что приводит к нестабильности результатов на графике.
- Максимальное время выполнения (около `0,91 мс`) при блоке `16x16` указывает на то, что данная конфигурация в текущих условиях эксперимента оказалась наименее удачной с точки зрения распределения ресурсов видеокарты `Tesla T4`.
- Наилучший результат зафиксирован при конфигурации `32x32` (приблизительно `0,79 мс`). Следовательно, на небольших матрицах увеличение количества потоков в блоке начинает давать преимущество за счет лучшего сокрытия задержек памяти.

### 3.3. При порядке равном 800

![Зависимость времени от потоков для N=800](Figures/Figure_N=800.png)

- C увеличением размера блока время выполнения стабильно снижается. Следовательно, объем вычислений стал достаточным для того, чтобы архитектурные преимущества параллелизма начали преобладать над случайными системными шумами.
- Наихудший результат показала конфигурация `8x8` (около `4,9 мс`), в то время как переход к блоку `32x32` позволил сократить время до `3,55 мс`.

### 3.4. При порядке равном 1200

![Зависимость времени от потоков для N=1200](Figures/Figure_N=1200.png)

- Наилучшее время выполнения (около `11,3 мс`) достигается при конфигурации блоков `16x16`.
- При переходе к блокам `32x32` время выполнения резко возрастает до `19,3 мс`, что делает эту конфигурацию менее эффективной, чем `8x8`. Возможно это из-за того, что число 1200 не делится нацело на 32, значительная часть запущенных блоков оказывается недогруженной, что приводит к нерациональному использованию вычислительных ресурсов.

### 3.5. При порядке равном 1600

![Зависимость времени от потоков для N=1600](Figures/Figure_N=1600.png)

- Увеличение размера блока ведет к существенному сокращению времени выполнения. Время выполнения уменьшается с `43 мс` для блока `8x8` до `26,5 мс` для блока `32x32`.
- При `N=1600` влияние накладных расходов на запуск ядра становится незначительным по сравнению с общим временем вычислений, что подтверждается плавным и предсказуемым видом графика

### 3.6. При порядке равном 2000

![Зависимость времени от потоков для N=2000](Figures/Figure_N=2000.png)

- Наблюдается устойчивое снижение времени выполнения при переходе от малых блоков к крупным: от `80 мс` для `8x8` до `62 мс` для `16x16`.
- Отсутствие аномалий, характерных для средних матриц, объясняется тем, что огромный объем полезных вычислений полностью нивелирует незначительные накладные расходы на краевые блоки.

## 4. Выводы

- Применение графического процессора `NVIDIA Tesla T4` позволило достичь значительного ускорения вычислений по сравнению с `CPU`. Для матриц порядка `N=2000` время выполнения сократилось с нескольких секунд до `51 мс`, что подтверждает преимущество архитектуры `CUDA` для массово-параллельных задач.
- Экспериментально доказано, что размер блока потоков существенно влияет на производительность. Наилучшие результаты на больших объемах данных показала конфигурация `32x32`, обеспечивающая максимальную загрузку вычислительных ядер и эффективное скрытие задержек памяти.
- Установлено, что эффективность параллелизации растет вместе с порядком матрицы. На малых масштабах (`N=200`, `N=400`) доминируют накладные расходы на запуск ядра, тогда как на больших (`N=1600`, `N=2000`) проявляется истинная вычислительная мощь `GPU`.
- Выявленная аномалия при порядке `N=1200` при блоке `32x32` подтвердила важность кратности размерности данных к размеру блока.
